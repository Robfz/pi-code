# pi-code — PR guide: decision map

Builds on [maps/2026-11-02-pr-review.md](maps/2026-11-02-pr-review.md) (`/pr`, PR mode, store, polling), which deferred the review guide.

## Findings
- [settled] F1: Linear's Guide: ordered sections, each with title, `NN / MM` counter, a why-explanation and file cards holding the section's diffs with expandable "N unchanged lines"; per-file Reviewed marks; prev/next between sections. Undocumented: whether a file's hunks split across sections, a leftover section, generation trigger (https://linear.app/docs/diffs, https://linear.app/changelog) — acknowledged
- [settled] F2: The `/pr` machinery (`prs.json` keyed by session file, hidden `refs/pi-code/pr/*`, `ls-remote` polling, `<pr>` context message, PR mode in the Changes view) exists and is reusable — acknowledged
- [settled] F3: The server has no workspace root or repo list: it knows only folders referenced by pi session headers (`GET /api/projects`) and pinned repos (`/api/sidebar`); `layoutOf` classifies `<repo>/main` repos; the only filesystem listing is `fs/dirs` prefix autocomplete — acknowledged
- [settled] F4: The review pane's tabs are Changes / Files / Tree (`review-state.ts`), active tab persisted per agentId in localStorage; phone's Diff page shows Changes and Files only. `/pr` works on a not-yet-prompted agent and sends its context prompt immediately; the server checks the URL's repo against the folder's `origin` — acknowledged
- [settled] F5: `POST /api/worktrees` fetches origin, runs `git worktree add -b <branch> <repo>/<name> <base>` (base default `origin/main`), opens a conversation there; 409 `worktree_exists` / `branch_exists`; removal keeps the branch. A worktree at the PR head means the PR is checked out on disk, unlike the `/pr` design's no-checkout premise — acknowledged
- [settled] F6: The URL flow converges with `/pr`: create the worktree, open a conversation, run the existing attach with the URL; store, refs, pinned SHAs, PR diff, polling and the guide are shared. The only divergence: after new pushes, Refresh moves the pinned SHAs but the worktree's checkout stays where it was — acknowledged
- [settled] F7: Git refuses to check out a branch already checked out in another worktree (e.g. your own PR's branch in its own worktree); fork PRs' head branches live in another repo, so locally they come only from `refs/pull/N/head` — acknowledged
- [settled] F8: Worktree removal keeps the branch by the worktrees map's choice (`maps/2026-09-30-worktrees.md`): it runs `git worktree remove` with git's defaults, so unpushed commits survive and removal needs no guard for them — acknowledged
- [settled] F9: The server can generate a guide (a) as an agent run: `pi --mode json --no-session`, read-only tools (`-t read,grep,find,ls,...`), an extension registering a `submit_guide` tool whose schema-validated args are the guide; or (b) as one tool-less model call with the diff in the prompt, like `auto-name.ts`'s `modelRegistry.streamSimple`. Today the server spawns pi only as `pi --mode rpc --extension <ext>` and makes no model calls itself — acknowledged
- [settled] F10: Settings live in server env vars (`PI_CODE_*`, `.env.local`, read at startup) or the web Settings screen (per-browser preferences); a server-side setting would need new server storage — acknowledged
- [settled] F11: Two ways to put the guide into the conversation: (a) an RPC `prompt`, which always starts a turn (the agent replies; shows as a user message, like the `<pr>` card); (b) a hidden extension command (like `pi-code-tree`) calling `pi.sendMessage({ customType, display: true }, { triggerTurn: false })`, which adds it to the context without a reply — acknowledged
- [settled] F12: Trust: a new worktree is a new path; pi-code opens its agent `awaiting_trust` when it has `.pi`/`.agents` resources and no trusted ancestor, and `/pr` attach refuses an agent awaiting trust. In JSON/print/RPC modes pi itself skips project resources for an untrusted path; under a trusted container a checked-out PR's own extensions and skills load — acknowledged
- [settled] F13: `origin/main` has keyboard shortcuts (`docs/design/10-keyboard.md`): a ⌘J leader then one key, commands listed in `features/keyboard/commands.ts`, handlers registered with `useCommand`; R is unbound; with a dialog open only H fires. This branch is already merged into `origin/main`, so the work starts from it — acknowledged
- [settled] F14: Review of this map (verified): reusing a pre-existing local branch conflicts with the hard reset on Refresh (drops the user's unpushed commits) and checks out code that may differ from the PR head; deleting only a branch "the review created" needs a durable marker git alone doesn't provide (a reused and a created branch look the same) — acknowledged
- [settled] F15: Review of this map (verified): without a checkout (`/pr`) or with a dirty review worktree left at the old head, the job's read tools see a tree other than the pinned diff (PR-added files missing) — acknowledged
- [settled] F16: Review of this map (verified): hunk boundaries depend on diff options, including the user's git config (`diff.context`, `diff.algorithm`), since `DIFF_FLAGS` (`git/git.ts`) pins neither; the same `base..head` can yield 1, 2 or 3 hunks. The Changes tab starts files collapsed past `EXPAND_MAX_FILES` 30 / `EXPAND_MAX_LINES` 3000 (`changes-view.tsx`) because every expanded file mounts a diff view — acknowledged

## Entry
- [settled] A PR review starts by pasting a GitHub PR URL into a small dialog with one URL field — user (dialog: agent's call, delegated by user)
- [settled] The dialog opens with ⌘J R, a new `pr.review` command in `features/keyboard/commands.ts` — user
- [settled] A "Review PR" button beside "New conversation" on Home (desktop and phone) opens the same dialog; it's the phone entry — agent's call, delegated by user
- [settled] A server-side registry of repos, populated with every `<repo>/main` repo pi-code has seen (sessions or pins) — user
- [settled] The registry matches a URL by the `owner/repo` parsed from each repo's `origin`, not the folder name (survives renamed folders; same check `/pr` already runs) — agent's call, delegated by user
- [settled] No two local repos share a GitHub repo, so the URL's repo identifies one local repo — user
- [settled] Errors, shown in the dialog: repo not in the registry; PR from a fork (out of scope); `pr-<number>` worktree exists; local branch exists; branch checked out elsewhere; conversation awaiting trust (in practice layout repos are trusted through their container) — user

## Review worktree
- [settled] The conversation runs in a new worktree `<repo>/pr-<number>`, then the existing `/pr` attach runs with the URL — user
- [settled] The worktree checks out a new local branch with the PR's head branch name, created at the PR head and tracking `origin/<head branch>` — user
- [settled] A PR has at most one review worktree; no routing between conversations of a worktree, so an existing `pr-<number>` worktree is an error — user
- [settled] A local branch with the PR's head name that already exists (checked out or not) is an error; the review always creates its own branch — agent's call, delegated by user (reusing one conflicts with the hard reset and branch deletion, F14)
- [settled] The branch carries a git-config marker (`branch.<name>.pi-code-review = <number>`) identifying a review branch; it's durable without a new store and goes away with the branch — agent's call, delegated by user (F14)
- [settled] Removing a worktree whose branch has the marker also deletes the branch (`git branch -D`), unpushed commits included; other worktrees keep today's behaviour — user
- [settled] On Refresh after new pushes, a marked review worktree that is clean hard-resets to the new head (covers force-pushes; commits made there and not pushed are dropped, recoverable through the reflog); a dirty one stays and shows a warning; plain `/pr` conversations get no checkout change — user (reset: agent's call, delegated by user)
- [settled] The review worktree follows the pinned head whenever it doesn't hold it: on every Refresh (so one left behind dirty is moved once clean) and on attach (a new worktree's branch may predate `refs/pull/<n>/head`); never while the conversation's agent runs a turn, which gets a warning instead — agent's call, delegated by user (review of stage 4: F2, F14)
- [settled] A review branch left by a removal whose `git branch -D` failed (marked with the PR's number, checked out nowhere) is deleted by the next review of that PR instead of answering `branch_exists` — agent's call, delegated by user (review of stage 4: F10)

## Guide generation
- [settled] The guide is generated server-side by a separate one-off job, not by the conversation's agent — user
- [settled] The job is an agent run (F9 a): read-only tools, guide returned through a `submit_guide` tool — user
- [settled] The job runs in a temporary detached worktree at the pinned head under the repo's common git dir (`<main>/.git/pi-code-guide/<id>`), removed when the job ends (leftovers removed before the next job in that repo); one path for `/pr` (plain clones included), clean and dirty review worktrees; it inherits the checkout's trust and stays out of every listing — agent's call, delegated by user (F15)
- [settled] The job loads that checkout's project resources (`.pi`, `.agents`) and context files (AGENTS.md / CLAUDE.md) like a conversation; a PR's own extensions run in the job, accepted for team repos — user
- [settled] Generated automatically on attach (URL flow and `/pr`) unless a guide for that diff is stored, and regenerated after each Refresh — user
- [settled] One job per guide key; a second request for a key already generating waits for it — agent's call, delegated by user
- [settled] A Refresh during a running job kills it and starts a new one; job state lives in memory, so a server restart loses a running job and the tab shows the error state with Retry — agent's call (least effort), delegated by user
- [settled] Default model Opus 5.5 (`anthropic/claude-opus-5-5`), configured through the server env var `PI_CODE_GUIDE_MODEL`, read with the rest of `loadConfig` (`.env.local` holds only web build options today) — user
- [settled] The finished guide is sent to the conversation's agent as a prompt, like the `<pr>` context: a compact card in the transcript, the agent replies (steers if running) — user

## Guide storage
- [settled] Guides are stored per PR diff, one file per `owner/repo#N@<baseSha>..<headSha>` in the data dir, pruned when no attached conversation pins that pair; forks, clones and repeat `/pr`s reuse it; Retry overwrites it — user accepted agent's recommendation
- [settled] Each guide file records a format version; a stored guide with another version counts as failed (error state, Retry) — agent's call, delegated by user (F16)
- [settled] Reviewed marks live in the browser, per section; regenerating the guide clears them — user

## Guide content
- [settled] Every attach generates a guide; the job's prompt tells it that a short PR gets a single section with its explanation — user
- [settled] Sections group individual hunks; one file can appear in several sections; a hunk may appear in several sections when the job deems it necessary — user
- [settled] Hunks no section claims are listed at the end under "Other changes" — user
- [settled] The job references hunks by ids pi-code assigns over the pinned diff (the pane's own hunks); unknown ids are rejected; a git hunk is the smallest unit, so nearby unrelated edits can't be split — user accepted agent's recommendation
- [settled] The PR diff pins its options (`-U3`, `--diff-algorithm=myers`) so hunks, and their ids, don't follow the user's git config; the Changes tab's PR mode uses the same diff — agent's call, delegated by user (F16)
- [settled] No suggested questions in sections — user
- [settled] Job prompt wording, labelled-diff format, section text format, and the registry file's format and pruning are decided at implementation within this map — agent's call, delegated by user

## Guide tab
- [settled] Shows only in PR-attached conversations, like the PR mode; the pane opens on it by default (URL flow, `/pr`, reopen); also on the phone's Diff page — user
- [settled] Carries the same one-line PR header (`#N title`, Merged/Closed chip, "Outdated · Refresh"); Refresh there also regenerates the guide — user
- [settled] Sections stack in one scrolling column under a sticky bar with the current section's title, `NN / MM` and prev/next (scroll to the section); the current section is tracked while scrolling — agent's call (fancier UX at small extra effort; the Changes view already has sticky headers), delegated by user
- [settled] Each section: title, explanation, then file cards (path, `+N −M`) holding its hunks — user
- [settled] Ticking a section's Reviewed collapses it, unticking expands it; no auto-jump to the next — user
- [settled] Past the Changes tab's thresholds (30 files / 3000 changed lines in the PR), file cards start collapsed, as in the Changes tab — agent's call, delegated by user (F16)
- [settled] Unchanged lines around a section's hunks can be expanded (the diff viewer needs both file versions, readable with `git show <sha>:<path>`) — user
- [settled] Selecting lines in a Guide hunk adds `@sha:path:N` references to the composer, as in the Changes tab — user
- [settled] While generating (on attach or Refresh), the tab shows a plain loading state; no progress, and no old guide during a Refresh — user
- [settled] A failed generation (model error, no `submit_guide` call, unknown ids, lost or outdated job) shows the error and a Retry button — user
