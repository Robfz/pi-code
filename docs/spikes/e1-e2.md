# Spikes E1 and E2: trust over RPC, command completion timing

Run against pi v0.87.1 (`/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent`). The scripts are in `scripts/spikes/`:

- `e1-trust-ext.ts`: a `project_trust` handler. `SPIKE_TRUST_MODE` selects `confirm` (the design's handler), `env-yes` (return yes without asking), `undecided`, or `sleep` (wait 3 s, then undecided).
- `e2-cmd-ext.ts`: `/spike-wait` (waits 3 s, then calls `notify`) and `/spike-throw` (throws after 1 s).
- `rpc-driver.mjs <cwd> <ext> e1|e2`: spawns `pi --mode rpc --extension <ext>` with extra args from `SPIKE_PI_ARGS`. It splits stdout on `\n` only, auto-answers `confirm` with `confirmed:true`, and prints timestamps relative to the spawn.

All runs used `--no-session` and throwaway directories under `/tmp`. The real `~/.pi/agent/trust.json` was backed up first and restored byte-for-byte afterwards (same sha1).

The log excerpts below are shortened. `[stderr]` lines come from the spike extension.

---

## E1: project trust over RPC

### Does the handler fire in RPC mode?

**Yes**, but with `ctx.mode = "rpc"` and **`ctx.hasUI = false`**. Setup: `/tmp/pi-trust-spike-1/.pi/settings.json` = `{}`, no saved decision.

```
  314ms [stderr] [spike-e1] project_trust fired cwd=/private/tmp/pi-trust-spike-1 ctx.mode=rpc ctx.hasUI=false spikeMode=confirm
```

`event.cwd` is the canonical path (`/tmp` → `/private/tmp` on macOS).

### Does `ctx.ui.confirm` round-trip over RPC at startup?

**No.** `confirm` resolves to `false` immediately and never emits an `extension_ui_request`:

```
  314ms [stderr] [spike-e1] confirm resolved ok=false after 0ms
  327ms [stderr] [spike-e1] session_start isProjectTrusted=false
  466ms << {"type":"extension_ui_request",…,"method":"setStatus","statusKey":"mcp",…}   ← first stdout line
  468ms << {"id":"s1","type":"response","command":"get_state","success":true,…}
```

The source explains it. `main.js` builds the trust context with `hasUI: isInitialRuntime && trustPromptMode === "interactive"`. In `cli/project-trust.js`, `confirm`/`select`/`input` return `false`/`undefined` whenever `!hasUI` or the mode isn't interactive. They never go through the RPC UI bridge, which doesn't exist yet at that point anyway: RPC mode wires up stdout/stdin only after the runtime has been created.

So the design's handler as written is a no-op, because its own guard (`ctx.mode !== "rpc" || !ctx.hasUI`) always returns `undecided`. Without that guard it's harmful: it saves `"no"` for every project.

### Does `get_state` block until trust is resolved?

**Yes.** `get_state` was written to stdin at 1 ms, and the `sleep` handler took 3 s. The response arrived only after trust resolution and `session_start`:

```
     1ms >> {"id":"s1","type":"get_state"}
   234ms [stderr] [spike-e1] project_trust fired … spikeMode=sleep
  3256ms [stderr] [spike-e1] session_start isProjectTrusted=true
  3331ms << {"id":"s1","type":"response","command":"get_state","success":true,…}
```

stdin is buffered, and pi emits nothing on stdout until startup, including trust, has finished.

### Does `remember: true` write `trust.json`? In what format?

**Yes.** pi writes it itself, holding the `trust.json.lock` proper-lockfile lock. The key is the **canonical (realpath) directory** and the value is a boolean. pi rewrites the whole file with keys sorted and 2-space JSON. From the `confirm` run (ok=false), then the `env-yes` run:

```json
  "/private/tmp/pi-trust-spike-1": false     ← after the confirm run (confirm auto-false)
  "/private/tmp/pi-trust-spike-1": true      ← after the env-yes run
```

The store also accepts `null` values; the TUI's "trust parent" option uses them to clear child entries.

### Does a saved decision still invoke the handler first?

**Yes.** The handler runs on every startup of a directory with protected resources, whether or not there is a saved decision. A yes/no answer overrides the saved entry, and `remember` overwrites it: the `env-yes` run flipped a saved `false` to `true`. `undecided` falls through to the saved decision:

```
=== mode=undecided (saved: true)
  192ms [stderr] [spike-e1] project_trust fired … spikeMode=undecided
  202ms [stderr] [spike-e1] session_start isProjectTrusted=true
```

This matches `core/project-trust.js`: `--approve`/`--no-approve` → extensions → `trustStore.get(cwd)` (closest parent) → `defaultProjectTrust`. With `--no-approve` the handler is **not** called:

```
=== --no-approve
  202ms [stderr] [spike-e1] session_start isProjectTrusted=false      (no "project_trust fired")
```

### What about a directory with no protected resources?

**The handler is not called**, and the project counts as trusted. This holds for an empty directory and for a bare `.pi/`:

```
=== /tmp/pi-trust-spike-2 (empty)
  201ms [stderr] [spike-e1] session_start isProjectTrusted=true      (no "project_trust fired")
=== /tmp/pi-trust-spike-3 (bare .pi/)
  205ms [stderr] [spike-e1] session_start isProjectTrusted=true
```

### E1 implication: design §1 is not viable as written, but a variant is

An extension can't ask the user at startup in RPC mode. The event itself works fine, though: it fires, it can block startup, and its `{trusted, remember:true}` result is persisted by pi with the correct canonical key and file locking.

**Proposed fallback:** the server asks, and the extension relays the answer.

1. **Before spawning**, the server works out whether a decision is needed. It checks for protected resources: `.pi/{settings.json,extensions,skills,prompts,themes,SYSTEM.md,APPEND_SYSTEM.md}` in cwd, or `.agents/skills` in cwd or an ancestor, excluding `~/.agents/skills`. It then looks up the closest saved decision in `trust.json` using the realpath of cwd and its parents. If resources exist and no decision is saved, the server asks the web client, over its own channel, *before* starting pi.
2. The server spawns pi with the answer in an env var, e.g. `PI_CODE_TRUST=yes|no`. The extension handler becomes:
   ```ts
   pi.on("project_trust", (event, ctx) => {
     const d = process.env.PI_CODE_TRUST;
     if (ctx.mode !== "rpc" || (d !== "yes" && d !== "no")) return { trusted: "undecided" };
     return { trusted: d, remember: true };
   });
   ```
   pi then writes `trust.json` under its own lock (verified by the `env-yes` run), so the server never writes the file. If the env var is absent, the handler returns `undecided` and the saved decision applies.
3. Spike-verified alternative: the server passes `--approve`/`--no-approve` and writes `trust.json` itself. This is worse, because the server would have to re-implement pi's lock and file format.

`hasSavedDecision` moves from the extension into the server, where it decides whether to ask at all. E3's unit tests move with it, and gain a "has protected resources" check. Resync the protected-resource list with `hasTrustRequiringProjectResources` in `dist/core/trust-manager.js` on pi upgrades.

**Required design-doc changes** (not made here): rewrite design/04 §1 around the pre-spawn server prompt and env relay. Drop the "`confirm` travels over RPC while the agent is starting" claim. Note that the handler runs even when a decision is saved, so the env var must be set only when the user has just answered.

## E2: command completion timing

### When does the `prompt` response arrive relative to the command handler?

**After the handler finishes.** In the run below, the response came 3 s after the prompt, right after the handler's final `notify`:

```
   329ms >> {"id":"1","type":"prompt","message":"/spike-wait"}
   329ms [stderr] [spike-e2] handler start … typeof navigateTree=function typeof setStatus=function
   329ms << {"type":"extension_ui_request",…,"method":"setStatus","statusKey":"pi-code:spike","statusText":"started"}
  3330ms [stderr] [spike-e2] handler end
  3331ms << {"type":"extension_ui_request",…,"method":"notify","message":"spike-wait done; typeof ctx.navigateTree=function","notifyType":"info"}
  3331ms << {"id":"1","type":"response","command":"prompt","success":true}
```

Source: `AgentSession.prompt` calls `await this._tryExecuteExtensionCommand(text)`, which awaits `command.handler(args, ctx)`, and only then calls `preflightResult(true)`. RPC emits the `prompt` response in that callback. The RPC loop doesn't await the prompt itself (`void session.prompt(...)`), so other commands keep being served while the handler runs.

A handler that throws produces an `extension_error` event followed by a **successful** response:

```
  6832ms >> {"id":"2","type":"prompt","message":"/spike-throw"}
  7834ms << {"type":"extension_error","extensionPath":"command:spike-throw","event":"command","error":"spike boom"}
  7834ms << {"id":"2","type":"response","command":"prompt","success":true}
```

### Is `ctx.navigateTree` available in the command context?

**Yes**, `typeof ctx.navigateTree === "function"`. It returns `Promise<{cancelled: boolean}>`, and its options are `summarize`, `customInstructions`, `replaceInstructions`, `label`. `ctx.ui.setStatus` is also forwarded over RPC as `extension_ui_request` `setStatus`, so the `pi-code:` channel works if it's needed.

### E2 implication: the completion signal becomes the `prompt` response

The response doesn't carry the handler's result, though, and a throwing handler still reports `success:true`. Suggested handling:

- **Completion** = the `prompt` response for the request id. Then resync the transcript.
- **Outcome**: `navigateTree` failures surface as an `extension_error` event with `extensionPath: "command:pi-code-tree"`. This event is emitted *before* the response, so the server can mark the pending request failed when the response arrives. `cancelled` (a `session_before_tree` handler cancelled the navigation) doesn't show up in the response. Either detect it from the resynced leaf (did the leaf move?), or keep a single `setStatus("pi-code:tree", {requestId, cancelled})` emitted before the handler returns, which the server reads when the response arrives. It no longer serves as the completion signal. Either way, the timing-driven status channel can go. Keep only the minimal result report if `cancelled` matters to the UI.
- **Hazard**: if the extension failed to load, `/pi-code-tree {...}` isn't a registered command, so pi treats it as a **user prompt and sends it to the LLM**. Before sending, the server must confirm `pi-code-tree` appears in `get_commands` (the extension's load status at spawn is enough).

**Design-doc change** (not made here): in design/04 §2, replace "Report completion via setStatus" with "completion = prompt response". Either keep `setStatus` as an optional result carrier for `cancelled` or drop it, and add the `get_commands` guard.
