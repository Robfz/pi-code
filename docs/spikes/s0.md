# Spike S0: entries and protocol shape

Run against pi v0.87.1 in `--mode rpc` with `--model anthropic/claude-haiku-4-5 --thinking low --session-dir /tmp/pi-code-s0/sessions/<name>`. `--session-dir` works in RPC mode: session files land there, and `get_state.sessionFile` points to them. Each run used a fresh scratch git repo under `/tmp/pi-code-s0/work/<name>`.

- Recorder: `scripts/record-fixture.ts`.
- Fixtures: `test/fixtures/*.jsonl`, described in `test/README.md`.
- Total model cost: about $0.22.

User-installed extensions and packages load automatically in RPC mode and were active in every run: pi-web-access, pi-mcp-adapter, and the `~/.pi/agent/extensions` set.

Excerpts below are raw fixture lines, shortened with `…`.

## Answers

### 1. Does `get_entries` return every entry type with the documented fields?

**Yes, for every type observed.** The `entry-types`, `compaction` and `bash-command` fixtures cover:

- `message`, with roles `system`, `user`, `assistant`, `toolResult`, and `bashExecution`
- `model_change` `{provider, modelId}`
- `thinking_level_change` `{thinkingLevel}`
- `session_info` `{name}`
- `label` `{targetId, label}`
- `custom` `{customType, data}`
- `custom_message` `{customType, content, display, details}`
- `branch_summary` `{fromId, summary, details, usage, fromHook}`
- `compaction` `{summary, firstKeptEntryId, tokensBefore, details, usage, fromHook, systemMessage}`

`usage` and `context_edit` were not exercised. Every entry has `id`, `parentId` and `timestamp` as documented.

```json
{"type":"label","id":"650fe44a","parentId":"df3e0ba0","timestamp":"2026-09-26T23:54:50.477Z","targetId":"835c093b","label":"s0-label"}
{"type":"custom_message","customType":"s0-msg","content":"s0 injected context","display":true,"details":{"k":"v"},"id":"6bce812f","parentId":"092d39db","timestamp":"…"}
{"type":"branch_summary","id":"110f6c17","parentId":"bd56be7b","timestamp":"…","fromId":"e28ebaf1","summary":"The user explored a different conversati…","details":{"readFiles":[],"modifiedFiles":[]},"usage":{…},"fromHook":false}
{"type":"compaction","id":"d96bc5d3","parentId":"08d40084","timestamp":"…","summary":"## Goal…","firstKeptEntryId":"ca59ac82","tokensBefore":69017,"details":{"readFiles":[],"modifiedFiles":[]},"usage":{…},"fromHook":false,"systemMessage":{"role":"system",…}}
```

Other observations:

- A fresh session already has two root entries before any prompt: `model_change` and `thinking_level_change`. So `leafId` is not `null` at startup.
- The first prompt persists a `message` entry with `role: "system"`, about 30 KB with the user's tools and extensions.
- `get_tree` nodes carry `label` and `labelTimestamp`.
- `fork` copies the labels on the kept path as new `label` entries.

### 2. Is the entry visible to `get_entries {since}` right after `message_end`?

**Yes.** In every fixture, a `get_entries {since}` sent right after `message_end` returned that message's entry. This held for user, assistant, toolResult and custom messages. For example, `plain-answer` lines 76–78:

```json
{"t":33815,"dir":"out","line":{"type":"message_end","message":{"role":"assistant",…}}}
{"t":33815,"dir":"in","line":{"id":"plain-answer-4","type":"get_entries","since":"32cbce11"}}
{"t":33818,"dir":"out","line":{"id":"plain-answer-4","type":"response","command":"get_entries","success":true,"data":{"entries":[{"type":"message","id":"69fe8e1c",…,"message":{"role":"assistant",…}}],"leafId":"69fe8e1c"}}}
```

`message_end` doesn't cover every new entry. These arrive **without any `message_*` event**:

- `bashExecution` entries from the RPC `bash` command. They are visible to `get_entries` as soon as the `bash` response is out.
- `session_info`, `model_change`, `thinking_level_change`, `label`, `compaction` and `branch_summary`.

The server must also re-sync entries after these responses:

- `bash`
- `set_session_name`, `set_model`, `set_thinking_level`
- `compact`
- `fork`, `clone`, `new_session`, `switch_session` (the session changes; do a full re-fetch, because the old `since` id fails with `Entry not found: <id>`)
- every `prompt` that ran an extension command (`/label` adds a label, and `ctx.navigateTree` adds a `branch_summary` and moves the leaf, with no event)

### 3. Are built-in slash commands sent via `prompt` executed?

**No.** They go to the LLM as plain user text. `prompt "/name foo"` started a normal agent run: the model replied that it doesn't know that command, and the next `get_state` has no `sessionName`. `prompt "/compact"` also started a normal run, with no `compaction_*` events. See the `slash-commands` fixture.

So the web client must implement built-ins itself: `/name` → `set_session_name`, `/compact` → `compact`, `/new` → `new_session`, and so on. Extension commands (`/label`, `/s0-dialog`) *are* executed. Their `prompt` response arrives only after the handler finishes, dialogs included, and no agent events are emitted.

### 4. What does `entry_appended` look like?

It is emitted only for `custom` entries appended through `pi.appendEntry()`:

```json
{"type":"entry_appended","entry":{"type":"custom","customType":"s0-state","data":{"n":1},"id":"092d39db","parentId":"650fe44a","timestamp":"2026-09-26T23:54:50.478Z"}}
{"type":"entry_appended","entry":{"type":"custom","customType":"web-search-results","data":{"id":"muj1rcxw73luxp","type":"search",…}}}
```

It was **not** emitted for any other entry type we created: `custom_message` (which gets `message_start`/`message_end` with `role: "custom"` instead), `label`, `session_info`, `model_change`, `thinking_level_change`, `compaction`, `branch_summary`, or `bashExecution`.

### 5. What precedes `agent_settled`? Does `agent_end` carry `willRetry`?

**Every run ends with the same three events:**

```
turn_end → agent_end {messages, willRetry:false} → agent_settled
```

`agent_end` does carry `willRetry`; it was `false` in every fixture, since auto-retry wasn't triggered.

- **Steering and follow-ups stay inside one agent run.** Each queued message becomes `queue_update` → user `message_start`/`message_end` at the next `turn_start`, with no extra `agent_end`/`agent_start`. Steering is delivered one message per turn, because `one-at-a-time` is the default mode.
- **The `abort` response arrives after `agent_settled`.**
- **These produce no `agent_*` events:** extension commands, `compact` (only `compaction_start`/`compaction_end`), `bash`, and `set_*`.

## Wire format vs docs: surprises

- **The system message is a streamed message.** The first turn emits `message_start`/`message_end` with `role: "system"` (sections + `toolsAdded`, ~30 KB) before the user message. It is also included in `agent_end.messages`. Reducers must ignore or collapse it.
- **User message content is an array:** `"content":[{"type":"text","text":"…"}]`, not the string shown in `json.md`.
- **`message_update` matches the docs.** The records are delta-only, with top-level `usage` and no `partial`. `usage` also carries `cacheWrite1h` and `reasoning`, which are documented in message-types.md but not shown in json.md. Assistant messages also carry `responseId`, `responseModel` and `rawStopReason`. The first `toolcall_delta` has `"delta":""`.
- **`tool_execution_update` differs by tool:**
  - bash: the first update is `"partialResult":{"content":[]}` with no `details`. Later ones are `{"content":[{"type":"text","text":"tick\n"}],"details":{}}`. The final `tool_execution_end.result` for bash has **no `details` key** (`{"content":[…]}`), except on abort (`"details":{}`).
  - read and edit: **no updates at all**. The edit result carries `details: {diff, patch, firstChangedLine}`.
  - subagent: `partialResult.details.results[].messages` holds the child's full transcript, including its system message, in every update, so updates are large.
  - web_search: `{content:[{text:"Searching … (0/1 complete)..."}], details:{phase, progress, currentQuery}}`.
- **`bash_execution_update` matches the docs:** `{"type":"bash_execution_update","id":"bash-command-1","delta":"one\n"}`, one per output chunk. A command with no output emits none. The response is `{"output":"","exitCode":3,"cancelled":false,"truncated":false}`. Truncated output adds `fullOutputPath`, and the updates still stream everything.
- **`extension_ui_request` field names match `rpc-extension-ui.md`:** `title`, `options`, `message`, `placeholder`, `prefill`, `timeout`, `notifyType`, `statusKey`, `statusText`, `widgetKey`, `widgetLines`, `widgetPlacement`, `text`. Details:
  - Fire-and-forget requests also have UUID ids.
  - Clearing omits the field entirely: `{"method":"setStatus","statusKey":"s0"}`, `{"method":"setWidget","widgetKey":"s0"}`.
  - `widgetPlacement` is present only when `belowEditor` is set.
  - `statusText` can contain ANSI escapes (pi-mcp-adapter's `"\u001b[38;2;…m🔌 MCP: 2 servers enabled\u001b[39m"`), so strip or render them.
- **A dialog timeout sends no event.** `{"method":"select","title":"S0 timeout select","options":["x","y"],"timeout":1500}` just resolves inside pi after 1.5 s. The client must dismiss the dialog itself using `timeout`.
- **A dialog can arrive in the middle of a tool call.** The subagent tool's `confirm` came between `tool_execution_start` and its first update.
- **Abort mid-tool adds an extra empty turn:**

  ```
  tool_execution_end {isError:true, result:{content:[{text:"Command aborted"}],details:{}}}
  → toolResult → turn_end → turn_start
  → assistant message_end {"content":[],"stopReason":"error","errorMessage":"This operation was aborted"}
  ```

  Its stop reason is `error`, not `aborted`. Abort during text streaming gives `stopReason: "aborted"` as expected.
- **`set_model` emits no model event.** Only `thinking_level_changed` fires, and only if the level changes: switching to sonnet-4-5 changed it from `low` to `high`. The model change is visible only through `get_state` and the `model_change` entry.
- **Other state events:** `set_session_name` emits `{"type":"session_info_changed","name":"s0 entries"}`, and `set_thinking_level` emits `{"type":"thinking_level_changed","level":"minimal"}`.
- **`compact` on a too-small session fails.** It still emits `compaction_start` plus `{"type":"compaction_end","reason":"manual","aborted":false,"willRetry":false,"errorMessage":"Compaction failed: Nothing to compact (session too small)"}`, and the response has `success:false`. Manual compaction needs more than `keepRecentTokens` (20k) of context.
- **`fork {entryId}` forks *before* that user message.** The new session holds the path up to its parent, and the response returns the message `text`.
- **`clone` needs a saved session.** On a session with no assistant message yet, it fails with `This session has not been saved yet. Wait for the first assistant response before cloning or forking it.` Sessions without an assistant message are never written to disk.
- **Session switches re-initialise extensions.** After `fork`, `clone` or `new_session`, extensions start again: the pi-mcp-adapter `setStatus` is repeated and the pi-web-access stderr warning appears again. No event announces the switch; only the command response does.
- **Startup noise:** stderr `[pi-web-access] Dynamic tool activation requires Pi 0.86.1 or newer; …` (a version mis-detection on 0.87.1), and an `mcp` `setStatus` request at the start of every session.

## Consequences for the design

- The entry sync can't rely only on `message_end` and `entry_appended`. It must also run after the command responses listed in answer 2.
- Built-in slash commands must be implemented client-side.
- Treat `message_start`/`message_end` with `role: "system"` as non-transcript records.
- The dialog UI needs its own timeout handling.

## Smoke test (real pi 0.87.1, through the server)

`scripts/smoke.ts` drives a running server over HTTP/SSE against real pi (haiku, thinking low); `scripts/smoke-pi.sh` adds a throwaway `/smoke-dialog` extension via `--extension`. Surprises the fixtures missed:

- **A `prompt` that runs an extension command is answered only when the handler returns.** `/smoke-dialog` got its `response` after both dialogs were resolved, not on acceptance. The fake pi replays responses instantly, so the 60 s command timeout never showed up: a dialog left open for a minute turned the prompt into `504 pi_timeout` (and the web composer restored the text). The server now sends `/…` prompts without a timeout.
- **Session changes don't refresh stats by themselves.** After `fork` / `clone` / `new_session` / `switch_session` (and compaction) the cached `get_session_stats` still described the previous session file until the next `turn_end`. The server now emits `stats` right after each `transcript_reset` from those paths.
- **Extension re-initialisation records arrive before the command response.** The new session's `setStatus` requests are published before its `transcript_reset`, so statuses and widgets from the old session are never explicitly cleared.
- **The system message is a persisted entry.** `get_entries` returns it as a `message` entry with `role: "system"` (~30 KB), so every transcript and snapshot carries it.
- **Models improvise.** Haiku answered "count to 300" with a `bash` tool call, and one turn ended with `stopReason: "stop"` and thinking blocks only (no text), so the finished notification's body can be empty.
- **pi sets `process.title` to `pi`.** `ps` doesn't show its argv; find server-spawned pi processes by parent pid instead.
