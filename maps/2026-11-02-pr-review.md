# pi-code — PR review mode: decision map

Builds on [2026-10-09-code-review.md](2026-10-09-code-review.md) (review pane, branch mode, line references) and picks up the deferred "PR/checks loop" of [2026-10-10-ui-overhaul.md](2026-10-10-ui-overhaul.md).

## Findings
- [settled] F1: No GitHub/`gh` integration exists; all git goes through `runGit`; "PR-style" today means local branch mode (merge-base(base, HEAD)..HEAD); the ui-overhaul map defers a "PR/checks loop" — acknowledged
- [settled] F2: `gh` 2.103 is installed and logged in on this Mac (Robfz, keyring, ssh); `POST /api/worktrees` exists but branches only from remote-tracking bases and 409s on an existing branch — acknowledged
- [settled] F3: Linear "Guides" (part of Linear Diffs, May 2026) split a PR into chapters, core change first, then its consequences, glue/secondary code grouped apart; each chapter pairs a why-explanation with its diffs; Guide tab beside the diff view, prev/next between sections, sections markable as reviewed; AI-generated for larger PRs (https://linear.app/docs/diffs, https://linear.app/now/code-review-should-be-fast) — acknowledged
- [settled] F4: A PR diff needs no checkout: `git fetch origin pull/N/head` (works for fork PRs) brings the head commit in without touching the working tree, so merge-base(base, head)..head can reuse branch-mode diff code; `gh pr view N --json` gives title, body, base/head refs, comments — acknowledged
- [settled] F5: The pi extension already registers hidden `pi-code-*` commands and hooks `before_agent_start`; extensions can also register agent tools, and tool calls reach the client through the relayed RPC event stream — acknowledged
- [settled] F6: A `/pr` command can live in pi-code's client/server (intercepted, never reaches pi, invisible to the pi TUI) or in the pi extension (works in the TUI too; can run `gh`, inject context with `pi.sendMessage`, persist data with `pi.appendEntry`; the server already reads `get_entries` and relays `extension_ui` requests such as `setStatus`) — acknowledged
- [settled] F7: Agent ids are ephemeral (new id on reopen or server restart); the session file is the only durable per-conversation identity; the review pane's mode/base live per agentId in tab memory, so PR mode needs new persistence regardless — acknowledged
- [settled] F8: Persisting the PR link: (A) server store `prs.json` keyed by session file (sidebar-store pattern), ~1-1.5 days, doesn't follow fork/clone, key exists only once pi flushes the file; (B) custom entry in the session file via a hidden `pi-code-pr` extension command (the server must not write pi's session file), read back by the catalog scan or transcript, ~1-2 days, follows fork/clone, survives restarts and devices, needs the agent idle, and a brand-new session isn't on disk until the first assistant reply — acknowledged
- [settled] F9: Ephemeral agent ids are pi-code-only: pi sessions have stable ids (UUID in the header, `pi --session <path|id>`); pi-code's agent id is a handle on one running pi process. The session path is known from `get_state` as soon as the agent starts; only the catalog skips it until the first reply flushes the file — acknowledged
- [settled] F10: With option A the extension isn't required: the server can run `gh`, store the link and send context through RPC. The extension only earns a place if `/pr` should also work in the pi TUI, or if the injected context should be a custom message (`pi.sendMessage`) rather than a user message — acknowledged
- [settled] F11: The client already implements built-in slash commands (`/new`, `/name`, `/fork`, `/clone`…) alongside pi's; without the extension, the only RPC way to put text into the conversation is `prompt`, which always starts an agent turn — acknowledged
- [settled] F12: The agent has no way to change pi-code's state: asked to refresh, it can update its own view (fetch, re-run `gh pr view`), but the pane's pinned SHA stays put unless pi-code gets a hook (an extension tool, or watching the agent's tool calls) — acknowledged
- [settled] F13: Existing hooks: the pi extension registers no agent tools; it hooks `project_trust`, `before_agent_start` (reference guideline), `session_start`/`agent_end` (auto-name) and a hidden `pi-code-tree` command the server invokes. The server does watch agent tool calls once: `pipeline.ts` reads `web_search`'s `details.curatorUrl` from `tool_execution_update` (allow-listed tool) to proxy the curator, and it schedules a git status check on every `turn_end` — acknowledged
- [settled] F14: No subscription is available for other people's PRs: `gh`'s `--watch` flags poll on a timer; webhooks (and `gh webhook forward`, dev-only, one per repo) need repo admin plus a public endpoint or GitHub's websocket. Cheap polling: REST `GET /repos/o/r/pulls/N` with ETag (304s don't count against the 5,000/h limit) or `git ls-remote origin refs/pull/N/head` (git protocol); both see pushes only, new comments need `/pulls/N/comments` and `/reviews` — acknowledged
- [settled] F15: `gh pr view` with no argument resolves the PR of the current branch, so `/pr` on a branch that has a PR is the same flow. A branch with no PR is a second variant: no metadata, comments or Outdated, context from local git, pane in branch mode; and since attachment is permanent, the conversation stays PR-less after the PR is opened — acknowledged
- [settled] F16: Non-interactive `gh pr create` refuses until the branch is pushed, so a quick draft needs `git push -u origin <branch>` first; `--draft --fill` takes title/body from the commits — acknowledged
- [settled] F17: The composer already sends prompts while the agent runs, as steer (default) or queued follow-up — acknowledged
- [settled] F18: Collapsed blocks in user messages already exist: attached text files travel as leading `<file>` blocks in the prompt text, which `splitFileBlocks` (protocol) splits out and `user-message.tsx` renders as collapsed `CollapsibleRow`s that expand to the content; the outline likewise parses `<skill name>` blocks. A `<pr>` block would follow the same pattern — acknowledged
- [settled] F19: Without a checkout the PR head isn't on disk. The diff already names a version (`@<sha>:./path:N`) when the working tree differs from the diffed side (`changes-view.tsx:79`), so PR-mode selections would reference the head SHA; but opening a version-named reference opens the current local file (documented limitation, `07-code-review.md:383`), which in PR mode shows the wrong content, or nothing for files the PR adds — acknowledged
- [settled] F20: Opening a file at a version needs no checkout: `git show <sha>:<path>` reads the object database, where `git fetch origin pull/N/head` already put the PR's objects. Fetched objects reachable from no ref (only `FETCH_HEAD`) are pruned by `git gc` after ~2 weeks, so keeping them means writing a ref in the user's repo — acknowledged
- [settled] F21: GitHub keeps `refs/pull/N/head` for closed and merged PRs (even with the branch deleted), so they fetch the same way. Merged PRs need one special case: their head is now in the base branch, so merge-base(current base, head) = head and the diff would be empty; the base must come from GitHub's recorded base SHA (`baseRefOid`) instead. Merged/closed PRs never go Outdated — acknowledged

## Scope & context
- [settled] Map lives in `maps/` — user
- [settled] Covers both other people's GitHub PRs and your own branch (before or after opening the PR) — user
- [settled] Main driver: view the PR delta in pi-code and discuss it with the local agent (intent, correctness, alternatives) — user
- [settled] Posting comments/reviews to GitHub goes through the agent running `gh`; no dedicated UI for it — user
- [deferred] Review guide (Linear-style grouping of changes) — follow-up by user's call; a natural short-term evolution, so this design shouldn't preclude it
- [settled] Entry point for a PR: start a conversation with the PR URL or number — user
- [settled] Checking out the PR head happens only on explicit request — user
- [settled] `/pr` with no argument attaches the current branch's PR; with no PR it says "No PR for this branch" and offers a quick way to create a draft PR; no PR-less variant — user
- [settled] Quick draft: a button in the "No PR for this branch" notice sends the agent a fixed prompt to push the branch and create a draft PR with `gh`, writing title and description from the changes; no auto-attach, the user runs `/pr` afterwards — user accepted agent's recommendation (agent handles push/fork/dirty edge cases; no "draft pending" state)

## Entry & command
- [settled] PR mode is entered through an explicit command (e.g. `/pr <url|number>`), keeping it deterministic — user
- [settled] `/pr` lives in pi-code (client + server), not the pi extension; not available in the pi TUI — user
- [settled] `/pr` gives the agent one structured context message: URL, title, author, state, description, base/head refs with exact SHAs, changed files with +/- counts, existing review threads (top-level and inline with path:line), and exact commands for the diff (merge-base..head-sha, no checkout), checking for new pushes, and posting comments via `gh pr review` / `gh api`; no full diff (context cost, stale after pushes) — user accepted agent's proposal
- [settled] `/pr` sends the context straight to the agent as a prompt; the agent replies right away — user
- [settled] `/pr` can run at any point in a conversation; once attached to a PR, the conversation can't switch to another PR or detach — user
- [settled] Refresh or `/pr` while the agent runs steers the current run, like a composer prompt (F17) — user
- [settled] `/pr` refuses with an error when the URL's repo isn't the conversation folder's GitHub repo, or the folder isn't a GitHub repo — user
- [settled] "The folder's GitHub repo" means the `origin` remote only; PRs on other remotes (e.g. `upstream` in a fork) are refused — user
- [settled] The `/pr` context message shows in the transcript as a compact PR card that expands to the full text — user

## Updates
- [settled] Pane and agent stay pinned to the head SHA captured at `/pr`; when the PR has newer pushes the pane shows an "Outdated" label with a refresh button — user
- [settled] The refresh button also sends the agent an update (new SHAs, commits, comments) as a prompt, so it replies — user
- [settled] No agent-driven pane refresh: asking the agent in prose only updates its own view; no `pr_refresh` tool — user, for simplicity
- [settled] pi-code polls the PR head (no subscription exists, F14) when you open or switch to the conversation and after each agent turn — user
- [settled] Polling uses `git ls-remote origin refs/pull/<N>/head` (git protocol over the existing ssh auth, no API rate limit; pushes are all Outdated needs); merged PRs aren't polled — agent's call, delegated by user
- [settled] Wording of the `<pr>` context block and the refresh update message is decided at implementation, within the settled field list — agent's call, delegated by user
- [settled] "Outdated" means new pushes to the PR head only; new review comments don't trigger it — user

## Pane
- [settled] PR mode header is one line: `#123 <title>` with the number linking to GitHub; a state chip only when merged or closed; "Outdated · Refresh" only when there are newer pushes — user accepted agent's slimmed proposal
- [settled] An attached conversation's pane opens in PR mode by default, right after `/pr` and on reopen — user
- [settled] PR mode works on desktop (review pane) and phone (Diff page); desktop is the primary target — user
- [settled] The PR delta is a third mode in the review pane's Changes view, beside Uncommitted and Branch — user
- [settled] A version-named reference opens the file at that version (server reads `git show <sha>:<path>`), lifting the `07-code-review.md` limitation everywhere — user

## Sidebar
- [settled] The sidebar marks PR-attached conversations with the PR number (e.g. `#123`) — user


## Persistence
- [settled] Conversation stays attached to its PR across reopen/restart/devices — user
- [settled] Stored server-side in a store keyed by session file (F8 option A) — user
- [settled] Store format: `<dataDir>/prs.json`, `{ [sessionFile]: { repo, number, state, baseSha, headSha, title } }`, written atomically like `sidebar.json` — agent's call, delegated by user
- [settled] Forks and clones inherit the PR attachment (pi-code copies the entry to the new session file) — user
- [settled] Fetched PR commits are kept by hidden refs that mirror the store: one `refs/pi-code/pr/<N>/<sha>` per pinned commit; on every store change (attach, refresh, delete, fork, prune of entries whose session file is gone) refs no stored conversation pins are removed — user accepted agent's refinement (forks/clones share PRs, so per-conversation deletion would drop commits others pin)

## Checkout
- [settled] A requested checkout happens in the conversation's current checkout (like `gh pr checkout`), not a new worktree — user
- [settled] Checkout is requested by asking the agent in prose; pi-code adds no checkout UI or command, and the agent handles a dirty tree — user, rare need
