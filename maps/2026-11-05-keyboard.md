# pi-code — Keyboard shortcuts: decision map

Builds on [2026-10-10-ui-overhaul.md](2026-10-10-ui-overhaul.md), which deferred "keyboard layer and ⌘K palette" to this map. Backlog item: "Keyboard shortcuts: switch conversation, new conversation".

## Findings
- [settled] F1: An installed Chrome app window keeps some ⌘ keys for itself: at least ⌘N, ⌘W, ⌘Q and ⌘T. The full list needs a manual keydown-logging test in the installed PWA; synthetic events can't check it. Acknowledged. Superseded by F5 and F16.
- [settled] F2: pi TUI Ctrl bindings don't carry over to a Mac browser. In the composer, Ctrl+P/A/E/K/B/F are macOS text-editing keys, Shift+Tab moves focus, ⌥+letter types special characters, ⌥↑/↓ move the cursor. Acknowledged.
- [settled] F3: `(pointer: fine)` doesn't detect a keyboard. An iPad with only a keyboard reads coarse. No media query detects a hardware keyboard. Acknowledged.
- [settled] F4: Modifier shortcuts can only fire with a physical keyboard, so a gate would only control hint/help visibility and unmodified keys (Esc, typing to focus). Acknowledged.
- [settled] F5: Chromium source says an installed app window reserves no keys, so the page sees ⌘N/⌘W/⌘T first. A normal tab reserves ⌘N, ⌘⇧N, ⌘T, ⌘W, ⌘⇧W, ⌘⇧T, ⌘Q, Ctrl+Tab, ⌘⇧[ ] and ⌘⌥←/→. This refines F1; the manual test is still the ground truth. Acknowledged.
- [settled] F6: ⌘1–9 are not reserved in Chrome, in a tab or in an app window, so `preventDefault` takes them over from tab switching. Safari is unverified. Acknowledged.
- [settled] F7: Sidebar order is Active (live agents) first, then pinned repo groups, then other groups. Collapse state is stored on the server. Clicking a live agent navigates to it. Clicking an exited agent restarts it, and clicking a session resumes it, which spawns a process. Acknowledged.
- [settled] F8: The Active section is sorted newest prompt first, so sending a prompt moves that agent to position 1 and renumbers the rest. A search query filters the section too. A 10th live agent or later has no key. Acknowledged.
- [settled] F9: No modifier family is free of all overlaps. ⌃⌥ comes closest: it overlaps VoiceOver when that's on, and third-party window managers (Rectangle and Magnet bind ⌃⌥ + arrows/letters by default). ⌘⌥ + letters clashes widely (⌘⌥I/J/U/B/L in Chrome, ⌘⌥D/H/M/W/Esc in macOS). ⌘⇧3–6 are screenshots. ⌥ + letter is how non-US layouts type characters such as @ [ ]. Acknowledged (user replied to it by asking about a tmux-style prefix).
- [settled] F10: A tmux-style leader (one chord, then a plain key) is feasible: a global keydown listener holds a pending state. It needs just one free chord, at two keystrokes per action. The second key has to be kept out of the composer, and the pending state is usually shown (tmux status, VS Code "waiting for second key"). Plain sequences without a modifier (GitHub's `g n`) don't fire in text inputs, and the composer usually has focus. Acknowledged; user likes the leader.
- [settled] F11: The app has one breakpoint, `DESKTOP_QUERY` = 64rem (Tailwind `lg`). Phones in landscape are 844–932px wide, which is wider than an iPad in portrait (768–834px). Width alone can't tell them apart. Height can: a landscape phone is about 430px tall. Acknowledged.
- [settled] F12: `AppShell` unmounts `<Sidebar>` when it's closed (`sidebarOpen ? <Sidebar/> : toggle`). The Active list is computed in the sidebar and the picker state lives there too, so a handler registered by the sidebar disappears with it. The composer already ignores keydowns where `isComposing` is set. Acknowledged.
- [settled] F13: On desktop, extension dialogs (`DialogHost`) and the trust prompt are non-modal sheets scoped to the conversation column, and the sidebar is deliberately left usable while they're open. The composer uses Esc to dismiss its slash menu. Acknowledged.
- [settled] F14: On iPad Safari, Safari's own ⌘ shortcuts may never reach the page (WebKit bugs 191768/192897; CodeMirror #1160: ⌘F fires no keydown). No source confirms whether ⌘J or ⌘1–9 reach the page in macOS Safari, Dock web apps, iPad Safari or iPad Home Screen apps; only a device test can. Acknowledged.
- [settled] F15: Safari Dock web apps and iPad Home Screen apps match `(display-mode: standalone)`, so they get the app context. iPadOS Safari reports itself as a Mac (`MacIntel`), so ⌘ labels are right there. Holding ⌘ on iPad shows the system shortcut overlay, which pages can't add to. Acknowledged.
- [settled] F16: User's test on macOS: In the installed Chrome app, ⌘J and ⌘1–9 (and ⌘K, ⌘V) reach the page and `preventDefault` stops Chrome's own action. Without the listener, ⌘+digit switches tabs as usual. Safari doesn't deliver ⌘1–9 to the page at all, so in a Safari tab the leader's digit has to be pressed without ⌘. User-reported.
- [settled] F17: User's test on macOS Safari: ⌘J reaches the page in both a tab and a Dock app. ⌘1–9 reach it in neither, so in Safari the digits only work as ⌘J then a plain digit, even in the app context. User-reported.

## Scope
- [settled] v1 = shared shortcut infrastructure, plus switch conversation and new conversation — user
- [settled] Key handling isn't gated by viewport or pointer. Shortcuts work at every size and simply can't fire without a keyboard — user
- [deferred] Command palette (⌘K). It gets its own scope later — user
- [settled] Keys work in both the installed PWA and a normal browser tab, and the tab doesn't take over the browser's own tab keys — user
- [settled] A tmux-style leader (F10) is the keymap everywhere: app window and browser tab — user
- [settled] The leader is ⌘J. It isn't in Chrome's reserved list (F5), so the page gets it first in both contexts — user
- [settled] In the installed app window, ⌘1–9 also work directly without the leader. In a tab they're ⌘J then 1–9, which leaves tab switching alone — user
- [settled] A pending indicator shows while the leader waits — user
- [settled] Esc cancels a pending leader — user
- [settled] The leader has no timeout. The indicator plus Esc cover a forgotten leader, as in tmux and VS Code — user
- [settled] The second key counts with or without ⌘ held, and it's swallowed, so ⌘J ⌘C doesn't copy — user
- [settled] An unbound second key is swallowed, cancels the leader, and shows a brief "not a command" notice. Placement is agent's call — user
- [settled] Esc while pending is swallowed, so it doesn't also dismiss the composer's slash menu — user
- [settled] Window blur cancels a pending leader — user
- [settled] Placement of the pending indicator is agent's call — user ("somewhere")
- [settled] Platforms are macOS plus Windows/Linux, with Ctrl standing in for ⌘ (Ctrl+J leader, Ctrl+1–9). Chrome on Windows binds Ctrl+J and Ctrl+1–9 but reserves neither — user
- [settled] The help screen, indicator and notices show the platform's modifier (⌘ or Ctrl) — agent's call
- [settled] Browsers in scope are Chrome and Safari, on macOS and iPadOS — user

## Infrastructure
- [settled] Shortcuts bind to commands, not straight to handlers, so a later palette can list and run the same commands — user
- [settled] Everything lives in `features/keyboard/`: `commands.ts` (static `{id, title, section}`, read by the help screen and a later palette), `keymap.ts` (bindings per app/tab context, chosen by the `display-mode` query), one capture-phase `window` keydown listener mounted in `AppShell`, and `useCommand(id, handler)` registration. Active-list commands register from `AppShell`, not the sidebar — agent's recommendation, accepted by user
- [settled] While a modal, sheet or menu is open, global shortcuts are off, except the help screen's own open/close key. Matches the common convention, and stops ⌘2 from navigating away under an open picker — agent's recommendation, accepted by user
- [settled] The non-modal conversation-scoped sheets (F13) count as open, so shortcuts are off while they show — user
- [settled] Popovers (model picker, branch picker) count as open too — agent's call, accepted by user
- [settled] A key pressed while shortcuts are off shows a brief "off while a dialog is open" notice in the leader pill, so it doesn't fail silently — agent's call, accepted by user
- [settled] The composer's `/hotkeys` stays TUI-only: it lists pi's TUI keys, which don't apply in the browser (F2) — agent's call, accepted by user
- [settled] Ignore keydowns where `isComposing` is set or `keyCode === 229`, and cancel a pending leader. The second check catches Safari's composition-commit key — agent's recommendation, accepted by user
- [settled] Digits match by `code` (AZERTY's digit row types `&é"…`). Letters match by `key` so they follow the user's layout, falling back to `code` when the character isn't a Latin letter — agent's recommendation, accepted by user

## New conversation
- [settled] New conversation: ⌘J C — user
- [settled] ⌘J C opens the project picker where you are, not via `/?new=1`, so Esc leaves you on the current view — agent's call, accepted by user
- [settled] New conversation, previous/next and help get no direct chord in the app window. They're leader-only — user

## Toggle sidebar
- [settled] Toggle sidebar: ⌘J B, plus ⌘B directly in every context, app window and tab. ⌘B isn't in Chrome's reserved list (F5); Safari is unverified — user
- [settled] The command is registered only where the docked sidebar exists (`DESKTOP_QUERY`). Below it, it isn't registered: ⌘J B is "not a command" and ⌘B goes to the browser. Opening the sidebar sheet from the keyboard is deferred — user
- [settled] The shortcut doesn't move focus, except when focus was inside the sidebar, whose contents swap on every toggle: then the toggle button takes it — agent's call

## Browser verification
- [settled] Direct ⌘1–9 work in the Chrome app window. Confirmed by the user's test (F16).
- [settled] ⌘J works as the leader in macOS Safari, both in a tab and in a Dock app. No fallback leader is needed (F17).
- [settled] In Safari, the digit after ⌘J has to be pressed without ⌘, because Safari takes ⌘1–9 itself (F16, F17). A documented limitation — agent's call
- [settled] Safari is detected from the user agent. In Safari, the help screen shows only ⌘J + digit, even in the app context, because direct ⌘1–9 never reach the page there (F17). The exact UA check is agent's call — user
- [blocked: manual keydown test on iPad with a hardware keyboard, next week | user] Whether ⌘J and ⌘1–9 reach the page in iPad Safari and Home Screen apps. Accepted by the user as an open question in the design doc. Until it's tested, every iPadOS browser follows the Safari rules, because they all run on WebKit (F14) — agent's call, accepted by user
